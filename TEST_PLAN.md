# Test plan

Phase 1: clean dependency install; actual dev-server startup; browser-render all nine requested routes and not-found; desktop/mobile navigation and no overflow; configuration missing/invalid/valid states; no Supabase client when config is invalid; render error recovery; lazy-loading state. Run npm run lint, npm run typecheck, npm test, npm run test:e2e, npm run build. No production database or wallet test claims in this phase.

Later phases: real reset/migrate/seed and multi-user RLS/storage tests; active/expired/returned/wrong-user/wrong-book/no-loan access; payment wrong-chain/token/sender/recipient/amount, fake hash, failed receipt, confirmation/reorg, concurrent replay/idempotence and refresh/multiple tabs; admin privilege escalation and contributor privacy; complete reader/admin device journeys. Fixture/provider doubles belong only in tests. No production mocks may ship. Reference the phase-specific gates in IMPLEMENTATION_PLAN.md.

Security assertions: secrets absent from tracked files/build output, protected books absent from public assets, UI state never grants authorization, every future content request uses server time/loan checks. Record unavailable tooling or credentials instead of claiming tests passed.

Phase 2: npm run db:reset applies migrations and uploads private original demo chapters; npm run test:db runs transactional pgTAP constraints/RLS tests and real Auth/PostgREST/Storage integration. Test identities are ephemeral, and no remote project is accepted by the Node harness. Repeat reset/test before acceptance. Generate types using npm run db:types, then run foundation lint/typecheck/unit/build/browser regression checks.

Phase 3: npm run test:catalogue tests the real local catalogue on desktop/mobile, search/filter URL persistence, public previews, per-book plans, draft/disabled-plan denial, checkout review without mutations, loading/empty/network recovery and no protected content requests. Only loading/error fixtures intercept test responses. Run existing missing-configuration browser checks and unit/lint/types/build. Inspect captured desktop/mobile screenshots.

Phase 4: run test:borrowing and test:borrowing:ui with the real local Edge server running. Cover unpaid/missing/wrong-user/wrong-book, concurrent idempotent checkout/completion, seven-day activation, return/repeated access denial, reborrow/expiry before cleanup, cancellation, malformed IDs and disabled-adapter refusal. Timestamp shifting exists only in privileged test fixtures. Desktop/mobile journeys cover refresh/resume, reading, return, history, transactions and sign-out. Also run database, catalogue and route regressions, unit tests, lint, TypeScript, typecheck:functions and build; inspect screenshots and verify development controls are absent from dist.

Phase 5: real local email delivery and OTP consumption; no password-only bypass; genuine ephemeral EOA signatures; concurrent/replayed/expired/wrong-user/session/origin/account/chain/purpose/secret proofs; service RPC denial; metadata spoofing; challenge rate limiting. Browser journeys cover email, signature rejection/retry, proof, refresh, account change and sign-out. Provider tests cover delayed detection, explicit Polygon switching, duplicate prompts, disconnect and stale replies. Real-device account permission passed; obtain actual Polygon/signature verification and wallet version/OS before declaring the phase complete.

## Phase 6 verification tests

Deno verifier tests cover exact transfer data/logs, wrong chain/sender/recipient/amount/token, native value, prequote/time checks, receipt mismatch, removed logs, malformed calldata, missing receipts, finality lag, canonical mismatch and RPC failure. Local database/API tests cover concurrent creation/prompt/finalization, direct RPC denial, wrong user, fake frontend completion/hash, private reading and global replay after return. Browser checkout tests deliberately substitute only the payment endpoint and wallet broadcast to verify rejection, pending state and refresh recovery; they do not prove mainnet payment acceptance. That final gate requires a user-approved real Polygon transaction.
